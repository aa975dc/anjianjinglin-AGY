**综合评分：架构 6.7/10｜质量 72/100｜需求符合度 65%。**

不出事时能用；一旦踩到上述 3 个 P0，后果从"热键静默失效"到"按键卡死在系统里"不等。**这 3 个 P0 合计修复量约 1 小时**，性价比极高，建议优先处理。

## 四、P0 缺陷清单（代码缺陷 · 3 条 · 均已实测复现）

### P0-A｜轮询停摆：一次异常让 F1/F2/F3 全部永久失效

- **位置**：`gui_simple.py:415-434`，`gui.py:1070-1095`（同构）
- **根因**：`self._poll_id = self.after(self.POLL_MS, self._poll)` 这行**重新武装**语句位于 `try / except queue.Empty` **之外**，且不在 `finally` 中。消费队列时任意一条 handler（`self.log()` / `_handle_action()` / `messagebox`）抛出**非 `queue.Empty`** 的异常，这行就被跳过，轮询从此不再排期。
- **后果**：热键线程仍在跑并把动作投进队列，但**主线程永不消费** → 按 F1/F2/F3 毫无反应、状态永不刷新、界面**零提示**（只写进日志）。用户面对的是一个"看起来正常但完全失灵"的窗口，且没有任何可操作线索。
- **实测证据**：注入 handler 崩溃后，队列项不再被消费并持续积压，日志仅留下 `Tk 回调异常`。
- **修复**（约 10 分钟，收益极高）：`after` 移入 `finally` 保证必定重新武装；队列内每条消息用独立 `try/except` 包裹，单条失败不拖垮整轮。
- **回归测试点**：`test_poll_survives_handler_exception` —— 让 `log()` 抛异常，断言轮询仍继续消费。

### P0-B｜长按住导致系统级卡键

- **位置**：`gui_simple.py:294`（`hold = max(1, int(self.var_hold.get()))`，**无上限**）+ `sender.py:156`（`time.sleep(max(hold_ms, 1) / 1000.0)`，**不可中断**）
- **根因**：完整版的 `profiles.normalize_step()` 会把 `hold_ms` 钳制到 600000，但**简洁版/迷你版的 `_collect()` 直接构造 step dict，完全绕过了这层钳制**。数值框虽设了 `to=60000`，手动输入不受限。实测 `999999999` 可直达引擎。
- **后果**：`hold` 期间 `sender.tap()` 卡在不可中断的 `time.sleep()` 里，`_stop` 事件无法打断。实测 `hold=3000` 时 `stop(join=True)` 2 秒超时后线程仍在跑；若此时用户强杀进程（或点"退出程序"），`engine` 的 `finally → release_all()` **来不及执行** → 按键以按下状态残留在操作系统里，**全局卡键，所有程序都受影响**。
- **修复**：①`_collect()` 补钳制（与 `profiles` 一致，如 `1 ≤ hold ≤ 60000`）；②`hold` 分片为可中断等待（复用 `engine._sleep` 的思路）；③`stop(join)` 超时后补发一次 `release_all` 兜底。
- **回归测试点**：`test_collect_clamps_hold`。

### P0-C｜提权重启丢命令行参数 → 脚本"看起来全没了"

- **位置**：`instance.py:61-68` 的 `_launch_target()`
- **根因**：该函数只返回 `(pythonw.exe, '"main.py"')`，**完全不读 `sys.argv[1:]`**，不传递 `mini` / `full` 模式参数。
- **实测证据**：`argv=['main.py','mini']` 与 `argv=['main.py','full']` 返回的启动参数完全相同，均不含模式。
- **后果**：从**迷你版**或**完整版**里点"以管理员身份重启"（目标程序以管理员运行时必然弹出此提示）后，重启出来的是**简洁版**。
  - 迷你版：丢置顶/位置/单值间隔体验。
  - **完整版最严重**：完整版的多步序列、发送模式、录制等存档在 `%APPDATA%\KeyPresser\settings.json`，而简洁版读写的是 `simple.json` → 用户看到的是**空白的界面和空白的脚本列表**，会以为"我做的脚本全没了"，实际只是换了一套存档。
- **修复**（约 30 分钟）：`_launch_target()` 追加透传模式参数，例如把 `main.py` 后面原样带上 `mini`/`full`。
- **回归测试点**：`test_launch_target_keeps_mode`。
- **分歧说明**：架构师定级 P0，QA 工程师定级 P1。本报告采纳 **P0** —— 理由是它发生在"用户被迫提权"这一高频场景（目标程序以管理员运行时每次启动都要走），且后果是用户直接感知的"数据丢失"错觉。

## 八、建议补充的功能点（按模块）

### 8.1 `gui_simple` / 未来单一界面
1. **3 秒待命倒计时启动**（P0-D，设计稿已定方案）—— 点按钮后倒计时并在发送前把焦点还给上一个前台窗口（`win32 SetForegroundWindow`）。这是**当前最高性价比的体验修复**。
2. **多步序列**（简洁版永久缺失的最常用能力）—— 多数挂机场景需要"每 5 秒按 space + 每 60 秒按 1"。当前简洁版只支持单键。
3. **随机抖动**（抗反挂机检测）—— 完整版有，简洁版没有。
4. **主窗口一键最小化 + F4**（P0-F）。
5. **深浅双主题**（P0-G）。
6. **运行态写入窗口标题**。

### 8.2 新增模块（合并架构的前置件）
| 新模块 | 职责 |
|---|---|
| `ui/capture_dialog.py` | 从 `gui.py` 抽出 `KeyCaptureDialog`，三方共用，切断反向依赖（P1-5） |
| `app/controller.py` | 无 tkinter 依赖的 `AppController`，承载引擎接线/热键/队列轮询/状态机，GUI 只做展示 |
| `app/settings.py` | 统一 `settings.json` + 旧 `simple.json` 迁移器 + debounce 落盘（P1-2/P1-8） |
| `app/theme.py` | 双主题 token，`ttk.Style(theme="clam")` + 自定义色板 |
| `app/tray.py` | 系统托盘（P2-6） |
| `tests/` | 纯函数单元测试 + `test_poll_survives_handler_exception` 等 4 条关键回归（P1-4） |

### 8.3 核心层（保持零改动，仅加固）
`engine` / `sender` 是"未改一行"的资产，但 P0-B 暴露了**调用方绕过校验**的问题。建议加固原则：**所有进入引擎的数值必须经过一层统一的 `validate_run_config()`**，而不是依赖每个 GUI 各自校验 —— 这样以后无论再增几个界面都不会重蹈覆辙。

## 十二、结论

**「是否符合我的需求？」—— 部分符合。**

- **功能内核层面：符合。** 你要的 F1/F2/F3 热键、全中文、简洁界面、迷你独立窗口（左上角 + 关掉不断后台 + 文件日志）全部做到，而且做法干净（核心层零改动、继承复用不分叉）。这部分可以放心用。
- **UI 重设计层面：不符合。** 你明确拍板的"合并单一界面 + 深浅双主题"至今只有设计稿，代码零落地；你提出的"一键最小化"只做在了迷你版，主窗口至今没有任何收起手段。
- **稳定性层面：有隐患。** 3 个 P0 都不在"日常顺利路径"上，但一旦踩到，后果分别是"热键静默失效查不出原因""按键卡死在系统里""脚本看起来全没了"。这些都不是崩溃式报错，而是**静默失灵** —— 这也是它们能藏这么久的原因。

**我的建议**：先花 1 小时把 3 个 P0 止血（性价比极高），再启动合并工程兑现你对 UI 的决策。合并工程本身也是修复 P1-1/P1-2/P1-3 的自然时机。
