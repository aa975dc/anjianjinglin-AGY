## 一、质量评价

**综合打分：72 / 100**

3–5 句判断：

1. **工程化底子扎实**：6 个核心模块（`engine/sender/hotkeys/keys/winutil/recorder`）经 `cmp` 逐字节确认与上游一致，未改核心只换展示层的策略正确，`gui_mini` 用继承而非复制也避免了双实现分叉；日志/异常接管（`applog`）、i18n 覆盖率（EN=ZH=199，实测零缺失）都做得干净。
2. **但存在 2 个高严重度缺陷**：① `_poll()` 结构决定了"任一 handler 抛非 Empty 异常 → 轮询永久停摆 → F1/F2/F3 全失效且界面无提示"（已实测复现）；② `sender.tap` 里按住时长用**不可打断**的 `time.sleep`，且界面**不校验数值上限**，导致 F3 在按住阶段失效、极端值可造成**系统级卡键**（实测 hold=3000 时 `stop(join=True)` 超时 2s 仍在跑）。
3. **有多处"设置静默丢失/丢失参数"**：目标窗口在目标程序未运行时被静默重置并写空（实测）；提权重启只带 `main.py`、丢失 mini/full 模式（实测），迷你/完整版提权后变简洁版。
4. **测试资产本身是短板**：`_smoke_test.py` 直接覆盖**用户真实** `%APPDATA%\KeyPresser\simple.json` 且不恢复（实测残留 `target="记事本"`）、硬编码 `C:\Users\G\...pythonw.exe` 不可移植、docstring 声称的 `_elevation_hwnd` 打桩**代码里并不存在**；纯函数（`parse_combo`/`events_to_steps`/`normalize_config`）零单元测试。
5. **文档第九节"验证结果"存在夸大**：列了"17 模块语法编译""中文字体可用性""停止延迟 10ms""三种界面端到端+退出码 0"等行，但 `_smoke_test.py`/`_launch_test.py` 中**并无对应断言**。

**结论先行**：常见路径（目标程序已运行、按住取默认值）能正常用；但上述 P0 一旦触发后果严重（热键全瘫 / 卡键），**建议先修 3 项再日常使用**（见第八节）。

## 二、缺陷清单（按严重级排序）

> 编号规则：`P<级>-<序>`。证据均来自源码行号或本次实测输出。

### 🔴 P0-1　轮询永久停摆：任一 handler 抛非 Empty 异常 → 所有热键静默失效

| 项 | 内容 |
|---|---|
| **严重级** | P0 |
| **缺陷描述** | `_poll()` 把 `while True` 整个消费循环包在 `try/except queue.Empty` 里，重新武装 `after` 的那一行在 `while` **之外、且不在 `finally` 中**。消费队列时任意一条 handler（`self.log()` / `_handle_action()` / `messagebox` 的 Tcl 异常等）抛出**非 `queue.Empty`** 的异常，会直接越过 `except queue.Empty`，**跳过** `self._poll_id = self.after(...)`，于是轮询**永久停摆**。此后 F1/F2/F3/F4 全部不再被处理，且界面上**没有任何提示**（异常被 `applog` 的 `Tk.report_callback_exception` 记进日志文件，用户看不到）。 |
| **触发条件** | 消费队列的任一 handler 抛非 Empty 异常。可复现路径（实测）：向队列注入一条会使 `log()` 抛异常的项 → 后续所有动作静默失效。另一条可及路径：`_check_elevation` 提权成功 → `on_close()` 销毁窗口 → 控制权返回 `_poll` 末尾，在**已销毁**的 root 上执行 `self.after(...)` → `TclError`（进程虽将退出，但结构上已越界）。 |
| **期望行为** | 单条消息处理失败不应影响轮询自身；`after` 重新武装必须在 `finally` 中，保证轮询永不因 handler 异常而中断。 |
| **实际行为** | 复现输出：`后续队列项 AFTER-MARKER 被消费？ False`；`队列仍积压？ True 剩余=[('log','AFTER-MARKER')]`；`日志出现 'Tk 回调异常'？ True`。即：handler 崩溃后**队列不再被消费**，热键动作堆在队列里永远无人处理。 |
| **证据（文件:行号）** | `gui_simple.py:415-434`（`try`→418，`while True`→419，`except queue.Empty: pass`→432-433，重新武装→**434**）；完全相同结构见 `gui.py:1070-1095`（重新武装在 **1095**）。实测：`kp_probe_b.py` → `[B1]`。 |
| **根因** | 重新武装语句既不在 `try` 内被异常保护、也不在 `finally` 中；异常路径下永远不会执行。 |
| **修复建议** | ① 把重新武装放进 `finally`：<br>`def _poll(self):`<br>`　try:`<br>`　　while True: ...(每项处理再用内层 try 包裹，单条失败仅记日志)`<br>`　except queue.Empty: pass`<br>`　except Exception: self.logger.exception("轮询异常")`<br>`　finally: self._poll_id = self.after(self.POLL_MS, self._poll)`<br>② 且"重新武装前先 `if not self.winfo_exists(): return`"，避免销毁后的 `TclError`。 |
| **回归测试点** | `test_poll_survives_handler_exception`：注入一条使 handler 抛异常的消息，随后注入一条哨兵消息，断言哨兵**被消费**（当前实现失败、修复后通过）。 |

### 🔴 P0-2　长"按住"时长导致按键卡死、F3/退出无法立即停止

| 项 | 内容 |
|---|---|
| **严重级** | P0 |
| **缺陷描述** | `sender.tap()` 在按下主键后用**不可被 `_stop` 打断**的 `time.sleep(max(hold_ms,1)/1000)` 保持按住。引擎的所有等待都走可中断的 `engine._sleep()`（`TICK=0.01` 轮询 `_stop`），唯独这里没有。因此：① 按住阶段按 F3 **不生效**，最坏要等 `hold_ms` 毫秒才释放；② 若此时用户退出程序，线程被强杀，`finally` 里的 `release_all()` **来不及执行** → **按键在系统层面保持按下**（键盘卡键）。叠加 `gui_simple._collect()` 对按住值**没有上限校验**（实测 999999999 直达引擎），可造成数天级卡键。 |
| **触发条件** | 任意界面把「按住」填成大值（默认 Spinbox 允许直接键入；`to=60000` 只约束箭头不约束键入），或任何 > 数十毫秒的正常长按窗口内按 F3/关窗。 |
| **期望行为** | 文档承诺"F3 硬停止：播放线程在 10 毫秒内退出，并在 finally 里 release_all() 防止按键卡住"。应保证**任何时刻** F3/退出都能立即释放按键。 |
| **实际行为** | 实测（`kp_probe_c.py`）：<br>`[C1]` 正常 hold=90 且在 delay 阶段停止 → `stop(join)` **2 ms**（符合"10ms"承诺）；<br>`[C2]` hold=3000 → `stop(join=True)` 耗时 **2000 ms（join 超时）且 `仍在跑=True`**；等 tap 自然结束（约 3s）后 `仍在跑=False`。即**按住期间 F3 完全失效**。<br>配合 `[B4]`：`hold=999999999 -> _collect 得到 hold_ms=999999999`（`profiles.normalize_config` 本会钳到 600000，但 `_collect` 没走这条路）。 |
| **证据（文件:行号）** | `sender.py:146-162`（关键在 **156** `time.sleep(max(hold_ms,1)/1000.0)`）；`engine.py:214-224`（`_fire` 调用 tap 后才是可中断的 `_sleep`）；`gui_simple.py:294-296`（`hold = max(1, int(...))`，**无上限**）；对照组 `engine.py:103-112`（可中断 `_sleep`）；`profiles.py:88`（`_as_int(...,1,600_000)` 说明本有设计上限）。 |
| **根因** | 按键"按住"语义与"可中断"语义冲突：上游把 hold 实现为普通 sleep；本地新增的 `_collect` 又绕过了 `profiles` 的钳制。 |
| **修复建议** | ① `_collect`（及迷你/完整版对应入口）对 hold/delay/cycles 做**与 `profiles.normalize_config` 一致**的钳制（hold≤600000、delay≤3600000、cycles≤1000000）；② 让 tap 的保持阶段可中断：把 `time.sleep(hold/1000)` 改成"把 hold 切成 ≤20ms 的分片 + 检查 `stop_event`"，或给 `sender.tap` 传入一个 `should_stop()` 回调；③ 兜底：`Engine.stop()` 在 `join` 超时后**主动补发一次 `sender.release_all(_held+当前按键)`**。 |
| **回归测试点** | `test_collect_clamps_hold`（999999999 → ≤600000）；`test_stop_interrupts_hold`（hold=3000 时 `stop(join=True)` 应在 ≤200ms 返回且 `is_running=False`）；`test_key_released_on_stop_during_hold`（停止后无按键残留）。 |

### 🟠 P1-1　保存的目标窗口被静默重置并写空

| 项 | 内容 |
|---|---|
| **严重级** | P1 |
| **缺陷描述** | `refresh_windows()` 在初始化时被调用；若已保存的 `target` 对应的程序**当前未运行**（不在窗口列表里），代码把 `var_target` 静默改回 `("当前活动窗口")`。由于 `var_key/var_hold/var_delay` 都挂了 trace、每次改动都会 `_save_settings()`，且退出时也会保存，于是**下一次保存就把 `target` 写成空串**，用户的目标窗口设置无声丢失。 |
| **触发条件** | 启动简洁版时目标程序尚未运行（"先开工具、后开游戏"是常见顺序）→ 随后任意一次保存（改按键/改间隔/关闭窗口）即丢失。 |
| **期望行为** | 目标窗口设置应保留；即使当前未运行，也应保留字符串，下次它出现时能选中，或至少不被静默清空。 |
| **实际行为** | 实测（`kp_probe_b.py` → `[B2]`）：存档 `target="记事本"`（记事本未运行）→ `init 后 var_target = '（当前活动窗口）'` → `重新写盘后磁盘上的 target = ''`。 |
| **证据（文件:行号）** | `gui_simple.py:236-237`（重置）；调用点 `gui_simple.py:70`（`__init__` 里 `refresh_windows()`）；保存链 `gui_simple.py:264` + `456-472` + `474-489`。 |
| **根因** | 用 `not in combo values` 当作"设置非法"的判据，把"目标程序暂时没开"误判为"设置无效"，且重置发生在保存时机之前。 |
| **修复建议** | 保留用户选择的字符串：`values = [ACTIVE_WINDOW, *titles, saved_or_current]`（即使不在列表也把它放进下拉），或仅当 `var_target` 为空/非字符串时才回退；**不要把"未运行"当"无效"**。 |
| **回归测试点** | `test_target_preserved_when_not_running`：存档 `target="记事本"` → 构造 App → `_save_settings()` → 断言磁盘 `target=="记事本"`。 |

### 🟡 P2-6　「无限循环 + 目标窗口一直不激活」时 F2 暂停表现不一致

| 项 | 内容 |
|---|---|
| **严重级** | P2 |
| **缺陷描述** | 引擎在 `_ensure_ready()` 里等待目标窗口变为前台时，循环内**只检查 `_stop`、不检查 `_resume`**。此时按 F2，`toggle_pause()` 会把 `_resume` 清掉并把界面状态改成"已暂停"，但播放线程其实仍在 `_ensure_ready` 里空转等窗口，直到窗口激活才真正进入暂停；界面状态与引擎实际状态**短暂不一致**。 |
| **实际行为** | 实测（`kp_probe_c.py` → `[C3]`）：目标从未激活时 0.8s 后**仍在等待**（`仍在跑=True`），说明线程停在 `_ensure_ready` 的等待循环里；此时 `_resume` 未被该循环感知。 |
| **证据** | `engine.py:136-159`（等待循环 **151-156** 只看 `is_foreground`/`is_window`/`_sleep`）；暂停检查点 `_wait_resume` 在 **212**，位于 `_ensure_ready` **之前**。 |
| **修复建议** | 在 `_ensure_ready` 的等待循环内也检查 `_resume`（未 resume 时视为"暂停中"、不推进），或把 `_wait_resume()` 放到 `_ensure_ready` 之后并在等待期间周期性调用。 |
| **回归测试点** | `test_pause_respected_while_waiting_window`。 |

### ⚪ 已核实：**不存在**的问题（澄清 team-lead 的两处担忧）

| 疑问 | 核实结论 | 证据 |
|---|---|---|
| 单实例互斥体在**异常退出**（任务管理器结束进程）后是否残留占用？ | **不会残留**。`instance.acquire()` 用**具名互斥体**且从未 `WaitForSingleObject` 占有，仅靠句柄存在判断；进程被杀时内核自动关闭所有句柄，最后一个句柄关闭即销毁该具名对象，下次 `CreateMutexW` 得到全新对象。`find_existing_window()` 亦不会被残留影响（窗口随进程消失）。 | `instance.py:24-40` |
| `_ensure_ready` 目标窗口从不激活时是否**无限等待**、停止是否失效？ | 会**无限等待**（这是"选了目标窗口就只在它激活时发送"的预期语义），但**停止仍有效**：等待走可中断 `_sleep`，实测 `stop()` **3 ms** 返回、线程退出、且等待期间**不注入任何按键**。合理，仅需 UI 状态明示（已有 `status.waiting`）。 | `engine.py:147-159`；实测 `kp_probe_c.py` → `[C3]` |

## 七、结论

**能否放心日常使用？** —— **有条件可以**：在"目标程序已运行、按住/等待取默认或常规值、全程用 F1 启动"的前提下，主流程可用。但当前存在 **P0-1（热键可能全瘫且静默）** 与 **P0-2（长按住可导致系统级卡键、F3 失效）** 两个高危缺陷，**不建议在无值守/无人看管场景长期运行**。

**最该先修的 3 个缺陷（按优先级）：**

1. **P0-1 轮询停摆** —— 把 `_poll()` 的 `after` 重新武装移入 `finally`，并对每条队列消息单独 `try/except`。这是"整体功能可用性"的底线，且修复成本极低（改 3~5 行，`gui_simple.py` 与 `gui.py` 各一处）。
2. **P0-2 长按住卡键 + 数值无上限** —— ① `_collect` 对 hold/delay/cycles 按 `profiles` 规则钳制；② 让 `sender.tap` 的保持阶段可中断；③ `Engine.stop` 超时后补发 `release_all`。这是"安全/不卡键"的底线。
3. **P1-1 目标窗口静默丢失**（与 P1-2 提权丢参数并列）—— 保留用户选择的目标字符串，并让 `_launch_target()` 回传 `mini/full`。这两条都是"用户的设置/上下文被无声改掉"，排查成本高、体感差。

其余 P1/P2（写盘频次、多显示器坐标、DPI、置顶持久化、隐藏无法找回、测试污染真实配置、文档夸大）建议在首个修复版本一并处理，并**补齐第四节的单元测试**作为回归门禁——尤其是 `test_poll_survives_handler_exception`、`test_collect_clamps_hold`、`test_target_preserved_when_not_running`、`test_launch_target_keeps_mode` 四条，直接覆盖本次两个 P0 与关键 P1。
